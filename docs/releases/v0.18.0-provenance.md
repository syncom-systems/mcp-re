## Infrastructure and harness failures, reported as such

None of these is a code result. Each was diagnosed before the retry that passed.

1. **Stage 5's client had no SDK.** The kind lane's client ran under the default `python3`,
   which has no `mcp-re` SDK, so stage 5 failed before any proof. Re-run with the prepared
   interpreter (`MCP_RE_CLIENT=sdk/python/.venv-cp314/bin/python3 …`).
2. **Proof 4's load generator was killed twice (`exit 137`).** No OOM in the VM's `dmesg` or
   the kubelet log. The load loop rode one long `kubectl exec` stream; #1182 now pipes the
   loop into the pod and runs it detached, and short execs poll for its summary. The next
   run passed with 0 drops.
3. **Proof 8's harness asserted a refusal the system no longer makes.** Since #1083 a
   serving replica that reads a vanished trust-epoch counter repairs it forward, so a
   replacement pod started while a peer was alive came up Ready under the repaired epoch, and
   the refusal grep also matched the peer's WARNING. #1182 scales the proxy to zero before
   removing the counter, matches the startup refusal in current or previous logs excluding
   WARNING lines, requires no Ready replica at any sample over 60 s, and fixes an EXIT-trap
   leak that dropped the port-forward cleanup.
4. **Stage 4 failed p99 once under contention.** The stage-5 kind cluster was still running
   in the Docker VM; rep 6 reported p99 22,518 µs. After deleting the cluster, 6/6 PASS.
5. **The complete verification run was dispatched on `rc/v0.18.0`**, a branch at `ffeafb22`,
   because `verification.yml` cancels an in-progress run on the same ref and `main` was still
   receiving pushes. A dispatch on a branch is a complete run.

## Publication

from a clean checkout of the final candidate was refused before the build started: `403 …
The billing account for the owning project is disabled in state closed` (project
`project-b19bbb5e-9be8-4fcb-a2f`, `billingEnabled: False`). The images `mcp-re-proxy`,
`mcp-re-inner-fastmcp`, `mcp-re-loadgen` and `mcp-re-slo-bench` do not exist at tag `0.18.0`,
and the `v0.18.0` git tag and GitHub release are held until they do, because a tag whose
deploy surface names absent images is an `ImagePullBackOff` waiting to happen. The tag, the
Cloud Build id and the four image digests are recorded here when publication happens.

## What v0.18.0 does NOT claim

- **No performance claim.** No SLO, capacity or throughput statement is made for v0.18.0;
  the local stage-4 figure is a regression measurement in a workstation class.
- **No GKE round.** The eight live proofs ran on a three-replica `kind` fleet with the
  identical harness, chart and images.
- **The closure record is about its target only.** `verification/closures/ffeafb22….json`
  and the final candidate's record are historical statements about those trees; they make no
  later tree fresh.
